What the MVP is

A deliberately small web harness around the existing geometry engine:

  • web/server.py — Python standard-library HTTP server; no FastAPI, no requirements, no database.
  • web/static/ — plain HTML/CSS/JS page.
  • /api/render — accepts design JSON, width, page, tolerance and split; calls clothoid_lab.cli.render; returns SVG, report, summary info and elapsed milliseconds.
  • /api/presets, /api/caps, /api/cap — four presets and the existing cap families.
  • The native engine is reached through ctypes (clothoid_lab/backend/bertolazzi.py).
  • The page loads presets/caps, edits design JSON, previews SVG, downloads SVG/JSON, and shows the report.

Design semantics are unchanged: millimetres at 1:1, +y up, standard 200 × 250 mm sheet, 10 mm ribbon (5 mm each side) where selected, 0.5 mm cap stroke. The SVG writer flips at output; design and JSON remain y-up.

Class I caps are cap-1 … cap-27; class II leaves are cap-pt-1 … cap-pt-9. In the UI, class II caps intentionally clear the ribbon width: constant rails on a two-edge leaf put a diamond at its point.

Tests: 96 pass, including four web tests in tests/test_web.py.

Remote

Cloud Run runs the same Python server in Linux. The build is split:

  1. Engine base (engine/Dockerfile, built by cloudbuild.engine.yaml): Debian bookworm installs clang and compiles vendored Clothoids and csrc/ into libclothoidlab.so; the runtime is python:3.12-slim plus libstdc++6 and that .so. Rebuild only when vendor/, csrc/, or scripts/build-native.sh changes.
  2. App image (root Dockerfile): starts FROM the engine base and copies clothoid_lab/, web/, and out/caps/. Every UI or Python change rebuilds only this thin layer.
  3. Process listens on $PORT (8080) with HOST=0.0.0.0.

An app-only .gcloudignore drops vendor/, csrc/, scripts/, and engine/, so an app deploy uploads about 100 files and never runs the compiler. A first thin deploy took 30 seconds; the engine base took 6m43s once.

The Linux .so is deliberately built inside Debian bookworm. A downloaded Ubuntu 24.04 artifact requires glibc 2.38 and will not run on the Debian bookworm runtime; do not substitute it without changing the base.

Local/remote parity

The local and remote apps are the same app at the same level: same web/ code, same 36 caps, same presets, and the same rendered result.

scripts/check-parity.py verifies:

  • index.html, app.js, style.css are byte-identical;
  • /api/presets and /api/caps match;
  • a cap-14 render produces the same SVG and report on both.
.venv/bin/python scripts/check-parity.py

The last check passed all seven comparisons. The two native libraries differ only by platform (Mach-O .dylib locally, ELF .so remotely); the output is identical at the app’s precision.

The limiting factor

It is not “Cloud Run cannot run Python, binaries, or C++.” It can. The limits are the runtime shape and the free allowance.

  1. Stateless, request-driven container. No persistent disk, daemon, background process, or shell. State belongs in a database, bucket, or client.
  2. One small instance. 1 vCPU, 512 MiB, concurrency 2, 60-second timeout. Rendering is ~0.37 s, so this is comfortable for this tool, not for batch or heavy CPU work.
  3. Cold starts at min 0. First request after idle is roughly 1–3 seconds; later requests are warm.
  4. Public unauthenticated endpoint. Anyone with the URL can spend the free allowance. That is the biggest practical risk.
  5. Build, not runtime. C++ is compiled by Cloud Build; the deployed container cannot compile, install, or mutate itself.
  6. Large source context. The ~240 MB vendored Clothoids tree is uploaded for a build, so deploys are slower than a small Python app.

Do we need a faster/paid tier for a few days?

No. Cloud Run is the same service; the free tier is a usage allowance, not a slower plan. Warm renders are already sub-second. The only useful speed purchase for a demo is min instances = 1 to remove cold starts; it costs a few dollars if left running, then set it back to 0. More CPU or memory is not justified for a 0.37 s render.

Lock-in: low

The application is a standard OCI container. The only Google-specific pieces are the project, billing, Cloud Build, Artifact Registry, and the service configuration. The code imports no Google SDK and reads only the standard PORT environment variable.

To move to Fly.io, Render, Railway, a VPS, Kubernetes, or another container host:

  1. Build the same Dockerfile there.
  2. Run it with PORT set to the host’s expected port and HOST=0.0.0.0.
  3. Point the host at the container.

The URL and IAM/billing plumbing change; the engine, UI, and tests do not. There is no database or proprietary data store to migrate. The commercial attachment is to the Google account/billing setup, not the code.

gcloud run services delete clothoid-web --region us-central1
# Optional and destructive: removes the whole project.
gcloud projects delete

Deleting the service stops runtime charges. The $1 budget is only an alert; it does not shut the service down.

cd /Users/thomaskelly/developer/clothoid-lab
gcloud config set project 

# engine base — only when vendor/, csrc/, or scripts/build-native.sh changes
gcloud builds submit --config cloudbuild.engine.yaml \
  --ignore-file=.gcloudignore.engine .

# app — every UI/Python change (thin upload, no compiler)
gcloud run deploy clothoid-web \
  --source . \
  --region us-central1 \
  --allow-unauthenticated \
  --memory 512Mi --cpu 1 --concurrency 2 \

  --quiet
gcloud run services describe clothoid-web --region us-central1 \
  --format='value(status.url,status.latestReadyRevisionName)'

The remote service does not see local edits until redeployed. The cap list is baked into the image; adding a cap JSON requires a rebuild.

Security and operations

  • Every route except /health requires HTTP Basic auth with a shared token. The username is ignored; the password is the token. The token lives in Secret Manager as clothoid-token and is mounted as CLOTHOID_TOKEN; the local copy is ~/.config//token, outside the repo.
  • /health is public and returns {"ok": true}. /healthz is intercepted by Google's frontend and is not used.
  • Bodies are bounded at 1 MB and designs at 200 segments. POST /api/render is limited to 60 requests/minute, burst 20, per client address; excess returns 429 with Retry-After. The limiter is in-process and resets on a cold start.
  • No accounts, roles or saved designs; the shared token is the whole access model. Rotate it with a new Secret Manager version and a redeploy.
  • No secrets or service-account keys are in the repository or image.
  • Logs and metrics are in the Google Cloud console.
  • The budget is an alert only. Delete the service to guarantee zero runtime spend.

Known issues and next steps

  1. Accounts and roles are still absent. The shared token gates the URL (W11) and a per-address render limit guards the allowance (W12), but there are no named users, saved designs or audit trail. Keep the token private and rotate it if it leaks.
  2. Cold starts with min 0; use min 1 only for a demo window.
  3. Large build upload (fixed for app deploys). The vendored C++ tree is uploaded only when rebuilding the engine base. App deploys are thin. The Debian build is deliberate: the Ubuntu 24.04 artifact needs glibc 2.38 and will not run on Debian bookworm.
  4. Static caps: new out/caps/*.json files need an app deploy (thin), not an engine rebuild.
  5. Class II width: UI clears ribbon width for cap-pt-*; do not add rails at the point.
  6. Platform libraries differ: local Mach-O .dylib, remote ELF .so.
  7. Mobile polish is responsive CSS only; not yet a phone-first editor.
  8. No accounts, saved designs, sharing, or database. This is an MVP.

Continuation commands

Two project-scoped, focused OpenCode commands make the next session cheap to start. They are modelled on the existing handoff/handon pattern in grid-8 and ornaments, but they carry only one action:

  • /fhandoff [focus] — squares the record in docs/HANDOFF.md, chooses one focused action, writes next-fhandoff.md with a two-line pointer, and commits only the handoff files.
  • /fhandon — reads next-fhandoff.md, follows its doc pointers, performs that single action, and stops. The operator runs /fhandoff when it is time to put the work down again.

They live in .opencode/commands/ and are available when OpenCode is opened in this repository. They are not global, so they do not appear in the other projects. The grid-8 and ornaments commands were not touched.
